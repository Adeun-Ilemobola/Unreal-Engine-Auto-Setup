# 6. Define a precise process ownership contract

Before implementation, establish explicit invariants.

### Invariant A — Process identity

A PID alone must never be considered sufficient proof of process ownership.

Process identity must account for relevant evidence such as:

- Executable identity.
- Process creation time.
- Expected command line.
- Project association.
- Operation identity.
- Wrapper and child relationships.
- Session ownership.

Determine which evidence Windows reliably exposes in the supported environment.

Do not assume unavailable process metadata can be reconstructed.

### Invariant B — No unrelated process termination

Never terminate a process unless the extension can establish that it belongs to the exact operation being managed.

An unknown or ambiguous process must not be killed automatically.

### Invariant C — No unsafe overlapping work

If an earlier build may still be active against the same project, the extension must not start a conflicting new operation merely because its original extension host disappeared.

An unconfirmed process must produce an appropriate blocked or recovery state.

### Invariant D — Recovery after host reload

When a new extension-host instance starts, it must safely determine whether relevant previous operations are:

- Still running.
- Confirmed completed.
- Terminated.
- Stale.
- Unknown.

Do not claim completion based only on missing in-memory state.

### Invariant E — Bounded recovery

Recovery checks must be bounded and must not permanently freeze VS Code.

If process state cannot be established, report the uncertainty and provide a safe user-controlled recovery route.

Never implement an automatic timeout that simply assumes an uncertain process has stopped.

### Invariant F — Workspace identity

Recovery records must remain associated with the correct project.

Workspace switching or opening an unrelated project must not transfer ownership or block unrelated operations incorrectly.

### Invariant G — Durable but minimal metadata

If operation metadata must survive a host reload, store only what is required.

Avoid secrets, unnecessary command output, or unbounded retained state.

Define atomicity, cleanup, expiration, and recovery behavior.

# 8. Recovery architecture

Investigate and implement the minimum reliable recovery mechanism.

Potential components include:

## 8.1 Unique operation identities

Create an operation identity that distinguishes one extension-owned execution from another.

It must survive the necessary lifecycle boundaries without relying on the VS Code process remaining alive.

Avoid introducing predictable or ambiguous identifiers.

## 8.2 Durable operation journal

Evaluate a small, versioned operation record.

Possible fields include:

- Operation ID.
- Project identity.
- Workspace identity.
- Operation type.
- Start time.
- Wrapper process identity.
- Known child identities.
- Requested build target.
- Latest durable state.
- Cancellation state.
- Recovery status.

Record only information actually needed for safety.

Use an appropriate extension-owned storage location.

Do not place volatile process metadata in the Unreal project source tree or VSIX package.

Do not assume a write to in-memory VS Code state guarantees crash durability.

If a journal is used, define:

- Atomic write behavior.
- Corrupt record handling.
- Schema versioning.
- Stale record detection.
- Recovery after partial writes.
- Cleanup of completed records.
- Retention of unresolved records.

## 8.3 Reconciliation on activation

On extension activation, inspect relevant unfinished operation records.

Determine whether the associated process can be positively identified.

Possible outcomes:

- Confirmed active.
- Confirmed no longer active.
- Uncertain.
- Invalid/stale metadata.

Do not conflate "not found" with "successfully completed."

If the old process exited while the extension was unloaded, report its execution result as unknown unless durable evidence establishes the outcome.

Recover the operation gate or block unsafe operations accordingly.

## 8.4 Cancellation of recovered work

Determine whether cancellation of a recovered process can be safely supported.

If ownership is positively established, allow an explicitly authorized termination path using the existing cancellation safeguards.

If ownership is not established, refuse termination and explain why.

Do not provide a control that promises cancellation but silently terminates a possibly unrelated PID.

## 8.5 Multiple VS Code windows

Examine what happens when two VS Code windows open the same project.

Determine whether the existing in-memory operation gate is sufficient.

If cross-window coordination is necessary, evaluate the smallest correct mechanism.

Any shared lock must address:

- Ownership.
- Crash recovery.
- Stale lock records.
- Process identity.
- Atomic acquisition.
- Release.
- Multiple project identities.
- Failure handling.

Do not implement an unsafe lock file based solely on timestamps.

If strong cross-window serialization cannot be established within the available scope, document the limitation and preserve conservative behavior.
